# Attack pass: a device in several pools

Non-author break-it pass on `docs/design-multi-pool-devices.md` (read at `94b34136a`, `0.3dev`), by claude-cd598f for claude-f36a7f. Method: the design read
against `app/poolhouse-node/src` (`tls.rs`, `net.rs`, `peer.rs`, `beacon.rs`, `board.rs`, `gov/roster.rs`, `gov/ops.rs`, `grants/spec.rs`). No test was run and no
node was driven; each finding names the line it rests on. "Hole" means the design as written does not hold; "ok" means it holds. Decisions already taken
(Q1 = a fresh device name per pool; Q2 = label keyed from a per-pool discovery secret renewed at each removal, slice 3b) are judged in section 3.

## 1. Findings, worst first

| # | Case | Attack | Verdict | Fix |
|---|---|---|---|---|
| F1 | Probe / cross-pool link | The join window answers an **unlabeled** dial with the window pool's real certificate (2.3, row 2). Device D is in pools A and B and opens a window for B. A member of A dials D with no label, gets a real certificate that is not A's, and learns D is in another pool and B's fingerprint. A window also tells any host on the network that D is open for a join. | hole | The window serves its own throwaway key, made when the window opens and destroyed when it closes. The join exchange already binds both certificate fingerprints (4, step 2), so the pool certificate is never needed before the code is accepted. The pool certificate is shown only to a labelled dial. |
| F2 | Replay | A label is a bearer token for a few minutes. `Net::connect` dials an address taken from a beacon or a stale address; whoever answers there (an address reused after DHCP, a spoofed beacon) receives a valid label and can replay it against any other address for the window, learning which of them answer for the pool. The doc's "means nothing to anyone who does not hold the id" holds for decoding, not for replay. | hole | Bind the MAC to the destination: input = nonce, minute and the pinned fingerprint of the certificate the dialer expects. A joiner with only a code sends no label (F1). Add a per-slot recent-nonce cache (bounded, 4096) so a label is used once per server. |
| F3 | Removed by others | D6 says a device retires on holding the signed removal "from any member, by the `acts` op". A removed device cannot fetch it: `Members::verify_client_cert` (`tls.rs`) kills the handshake of a Revoked certificate with an alert, and `peer.rs` `dispatch` answers `acts` only to a non-Unknown standing. So the removed device never receives the removal, never retires, keeps its key, keeps beaconing and dialling, and the 3-day clock never starts. The only signal it sees is the TLS alert that the design correctly refuses to trust. | hole | (a) The remover pushes the signed removal once to the removed device's last address, and every member pushes it on the next dial. (b) A Revoked client completes the handshake and gets one answer, the removal act naming it (self-verifying against the charter it holds); every other op is refused. Then the alert-hint in `refusal_hint` can go. |
| F4 | Leave delivery | D6 step 4 sends the signed `leave` once, best effort, and step 3 has already destroyed the key. If the send fails (airplane mode, no address held, a member down) the act exists only on the leaver, can never be re-sent over the member protocol (no certificate), and the pool lists the device as active for ever. Under Q2(b) "every secret of the slot" is destroyed too, so the leaver cannot even build a label. | hole | Keep the signed act and the discovery secret in the frozen slot for the whole frozen period and retry delivery on a schedule until one member acknowledges; add a self-verifying `leave_notice` op that any certificate (a throwaway one) may call, since an act authenticates itself. Destroy the signing key at once, the discovery secret at the end of the frozen period. |
| F5 | Leave is not final in the code | The design says the old certificate "stays `left` for ever" (D7, section 3). `gov/roster.rs` says the opposite: "a `leave` is undone by a later `admit`", and the winner is the later `at_ms`, a time the signer writes. So a backup or clone of the old key (file custody, a Time Machine copy) is re-admitted under its old fingerprint, and a key holder can future-date a `leave` over a rejoin. Slice 1 ships rejoin of the same certificate before slice 3. | hole | Make `leave` a union like `remove` (`roster.rs` `removals`: "does not come back"): a left fingerprint is never admitted again, so D7 holds from slice 1. Slice 1 then refuses a rejoin of the same certificate until slice 3 gives it a new key; the existing HANDOFF limit stays one slice longer. Test: leave, admit the same fingerprint, still `Left` on a device that sees the acts in either order. |
| F6 | Leave cut | Section 3 step 1 puts a self-chosen cut in the `leave`. `Board::cut` keeps "the least ever named" and truncates the log (`log.truncate`). A stolen or cloned pool key signs a `leave` with seq 0 and every member loses everything that device wrote, for good. A cut above the truth reserves seqs for a later writer. Today only an admin's `remove` carries a cut, computed from the admin's own copy; `close_removed` only honours a cut for a removed (Revoked) writer, so a Left device is not covered by it either. | hole | A leave's cut is advisory: each member closes the leaver's logs at the tip it holds when it first sees the act, never lower than the highest tip it has ever held and never above what it holds. Name `Left` in `close_removed`. Test: a leave naming seq 0 truncates nothing a member held. |
| F7 | Downgrade / takeover by whoever is present | D9 lets a device in **no pool** join an `open` pool it hears. Section 2.1 returns a device that leaves its last pool to exactly that state. An attacker on the segment who beacons an open pool with the project key of the repository (public for any public repository) gets the victim into the attacker's pool within 5 seconds of a leave or a removal, with no ask. Move is safe (join first); a plain leave is not. | hole | A device that has ever held a slot (any tombstone, or a flag in `slot.json`) never auto-joins; only a fresh install with no tombstone does. The leave card adds no sentence; the behaviour is the safe default. |
| F8 | Malicious agent (confused deputy) | An agent registered to a board of pool A reads A's boards, which A's members write. An injected instruction there asks for `leave`, `remove` or `add-device` with `--pool B`. The doc stops the silent default but allows the explicit one, so the cost is one card that names B. This turns every shared board into a lever on the person's other pools. | hole | The node refuses a pool-level request (`pool_leave`, `member_remove`, `add_device`, `admin_manage`, `inbound_consent`, `shard_consent`) from a session whose board is in a different pool; such an act comes from the person's own app or phone, or from a session of that pool's boards. The card says "asked by an agent working in 'A'". |
| F9 | `*` grant refusal | (a) `grants/spec.rs` `check_resource` and `covers` accept a prefix before a final `*`; refusing only the literal `*` leaves `0*` (about one pool in sixteen), `ab*` and the like. (b) A grant is a board entry (`issue`, scoped to a board). One for pool B written on a board of pool A replicates to every member of A and discloses B's id (the Q2(a) label key) and alias. (c) A standing grant for `pool_leave` on a pool, valid up to a year, would let an agent leave with no card, which the design text ("grant ... one tap on a card") contradicts. (d) Grants cannot be revoked in a frozen (read-only) board, so "grants scoped to the pool are removed" cannot be done by an entry. | hole | Pool-level actions take an exact 32-hex pool id (no wildcard of any kind) and `uses: 1`, or are not grantable at all and always raise a card. Store pool-scoped grants in the pool's own history board or a device-local table, never on another pool's board. A grant naming a frozen or gone pool is void by derivation. |
| F10 | Board names | A board id is a device-wide name (2.5). Pool B, joined later, can offer a board called like one of D's boards of pool A or of the local pool, or squat the name D's repository will want (`.poolhouse/project.toml` pins one). D's sync either merges B's entries into A's board and pushes A's entries to B, or skips that name, and a skip is an oracle: B's member lists names and watches which ones D never pulls. A squatted name also breaks the project ("This folder's board is in 'lab'"). | hole | The on-device board id carries the pool (`<pool8>/<name>`); the wire name is the pool's own and is looked up only inside the connection's pool. Sync takes every name the pool lists with no reference to other pools. Test: pool B lists a board named like A's; D pulls it like any other, into its own namespace, and A's board is untouched. |
| F11 | Takeover / social | The frozen-board question "That project's board was in 'lab', which you left. Use 'team'?" says the answer "makes or adopts" a board in the new pool. Adopting the frozen board's entries into pool B discloses A's content to B's members on one tap. | hole (wording) | Define it as "makes a new, empty board in 'team'"; copying is a separate named card ("Copy 214 entries from 'lab' into 'team'?"). |
| F12 | Approval fatigue | "64 waiting requests shared 16 to a pool": 4 pools at 16 fill all 64 and starve the other 12. | hole (arithmetic) | Per-pool cap = max(2, 64 / pools held), plus the device-wide cap; the ledger of twelve asks stays device-wide. |
| F13 | Side channels in label handling | (a) "At most 16 MACs, always all of them" is read as all existing slots; the time then grows with the number of pools. (b) A window of "a few minutes either side" multiplies the MACs unless the minute rides in the label. (c) The throwaway is a key and certificate made per connection, the real slot a prebuilt config: a prober sees the cost difference, and an unlabeled flood costs keygen and signing per connection, ahead of authentication, in the thread-per-connection `accept_loop` with no cap. (d) A malformed SNI is aborted by rustls before the `Acceptor` yields, so it gets an alert while a well-formed wrong label gets a certificate. (e) The label is DNS-name shaped: at most 63 characters a label, and no uppercase games. (f) A wall-clock minute makes a device with a clock off by more than the window unreachable; the failure is indistinguishable from a refusal ("not the one pinned"), which is a new silent failure for the exact person with a wrong clock. | hole (minor, one pass) | Always do 16 MACs (dummies for empty slots) over a minute carried in the label; throwaway certificates from a small pre-made ring rotated each minute; per-source and global caps on unauthenticated handshakes and a deadline on the ClientHello read; treat malformed SNI as unmatched (uniform answer); and when a labelled dial reaches a throwaway, say "that device did not answer for this pool; check that both clocks are right". |
| F14 | Move / ordering | D8 (join first, then leave) is right. Gaps: (a) the leave is a sequence (history row, sign, close, destroy key) with no write-ahead state, so a crash after the signature and before `destroy` leaves a live key, an active slot and a signed act; (b) a pool's admin who hands out a code to a person gets a `move` card that ends the person's membership in A ("Move this computer from 'lab' to 'team'?"). | hole (a), ok (b) | (a) Persist `slot.json state=leaving` before anything else; refuse requests from then; boot resumes the sequence. (b) Cards for pool-level acts always show the first six digits of the pool id, not only "when two aliases read alike" (a stranger's "lab" must not look like the person's). |
| F15 | Rejoin | "The frozen boards ... are dropped once the rejoin has synced; nothing is lost" is false for entries that never reached a member (offline writes, a pool of one). | hole (data loss, wording) | The leave card and the rejoin line say so: "Entries that never left this computer are deleted after 3 days." Drop the frozen copy only after the person's yes when it holds rows no member has. |
| F16 | Busy answer | "A `busy` answer says only that the device is busy" still tells a member of A when D works for B (timing of busy periods, queue wait behind B's job, job length). | accepted risk, name it | Add to the "remains" column; make a remote request's `busy` immediate (never queued behind another pool's lease). |
| F17 | Facts in `hello` | `peer.rs` `hello` returns to any certificate: `pool` id, `fingerprint`, `board_fingerprint` (the device key), `network`, build id, seq and `pinned`. The design narrows it for a non-member; for members of both pools the build id, `pinned`, `network` and the instant a build changes are identical in both. | hole (list) | State the whole member-visible set in 2.3 and per-pool or coarsen it: `board_fingerprint` is the pool key's; `network` and the build update instant stay a named link (Q1). |
| F18 | Frozen slots | Frozen slots do not count toward 16 and have no cap; join/leave churn (each a tap) grows disk for 3 days a time. | hole (minor) | Cap frozen slots at 16 as well. |

## 3. The two decisions already taken

**Q1, a fresh device name per pool. Holds for the name, does not close the link.** Conditions: (1) the name is random, never derived from the computer's name,
hostname or a hash of them (a derived name is linkable by anyone who can guess the hostname); (2) the person's own list shows "this computer" beside it, so
recognition does not rely on a shared name, and a rename in one pool is not offered in another; (3) the doc keeps the sentence that address, port, hardware,
build instant and online pattern still link (F17), because a stable fingerprint was the headline reason for D3 and a stable name is a weaker version of the same
thing. Q1(b) costs the approval cards nothing they have today: a card already names the other device by the name the pool knows.

**Q2, label keyed from a per-pool discovery secret renewed at each removal. Better than the pool id, with five gaps that must be in slice 3b.**
The pool id is a hash of a charter every joiner and every card holds, so as a MAC key it is not a secret, and a single captured label allows an offline
test of candidate ids. The discovery secret fixes both. Gaps:
1. **Renewal at leave as well as removal.** A leaver keeps the secret, and a leave is not a removal. Any leave or removal triggers a renewal by an admin.
   Authorship is admin-only (routine class): the new secret rides sealed to each remaining member's pool key in the act, so a malicious member cannot split
   the pool by sending the secret to some. Check the act size cap against 16-admin charters and large pools.
2. **A member that was offline during a renewal is locked out**: every server rejects its old label as unmatched. The servers accept the previous epoch's
   label for a bounded grace (a day of awake time); the removed member learns only that the address answers during that day, against for ever today.
   Name this as the accepted risk. The member then learns the new secret from the acts it fetches.
3. **Beacons must move to the same secret.** The sealed beacon of `pools-and-serving.md` 4.2 is keyed from the id; a former member still decodes every
   beacon on the segment, which defeats the renewal.
4. **F4:** the secret outlives the key during the frozen period so a leave can still be delivered.
5. **The secret is stored in the slot, wrapped by the custody secret, destroyed with the slot**; a stolen directory with a file key carries it (same as the
   pool key).

## 4. What I did not verify

Whether grants live only in a replicated board (F9b rests on `parse_issue` taking an `issue` entry with a `board`); the full list of member-only ops beyond
`shard_*`, `landing`, `landtrust`, `build` and `probe` (the claim in 4 step 3, "the new pool can do nothing on the device a stranger could not", needs that
list written down and tested); `mail.rs` and `subs.rs` across a frozen board; the size caps on an act carrying a renewal. No attack in this note was run.
