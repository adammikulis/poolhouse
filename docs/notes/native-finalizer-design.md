# Native pool approval computer: design and offline impact

Status: design only. Administrative trust assumptions below are accepted for this phase-0 design. **The availability change is pending root's decision; implementation is not authorized.** Independent review has approved the conditional architecture and its ten-attack analysis, not an installed system or hardware assurance.

Source baseline: development `01904df4c100a5330fc3bd3aff02df31b824dd9f`. That baseline has 13 governance act kinds and still exposes key-count mode. Accepted person-registry checkpoint `c70e50eff7df9c62c87e0dfcac84030b02a7abc0` adds `person_add` and removes key-count mode; its integration is separate. This proposal requires distinct admitted Person IDs throughout and must not restore key-count voting. Native trust, finalization and transfer acts do not yet exist in either baseline.

## Decision and trust boundary

One explicitly enrolled protected approval computer is pinned in the signed founding charter of a Native-capable pool. It orders changes that already satisfy the pool's authorization rules against one durable current head. It contributes **no person vote**, admits no person or issuer implicitly, and lowers no quorum. Its root-owned service reconstructs and verifies transitions; it exposes no operation that signs an arbitrary caller-supplied hash.

This is administrative trust in the enrolled computer's operating system/root custody, genuine protected approval surfaces, honest durable-write acknowledgments, awake clock, and private state that is neither cloned nor rolled back. A consistent privileged snapshot rollback or cloned private store is outside this assumption and is not detected by the protocol. This is neither hardware attestation nor Byzantine fault tolerance. Supported tooling provides no private-key/store export, restore, migration or automatic reinitialization. Existing person-only installation, OS approval and credential boundaries remain intact.

The pending availability choice is precise: **all acknowledgments that change shared governance authority require this computer**, including routine actions, not just sensitive changes. Drafting and a bounded local queue remain available. Existing serving uses the last finalized authority state; locally stopping serving or disconnecting never waits for this computer. A local queue is not a second authority ledger.

## Actual actions and offline impact

Here, "offline" means the approval computer is unreachable; other pool devices and networks may still be operating. Current source has no such computer dependency: a node can validate and fold held acts locally, subject to its available signer, quorum, grants, network evidence and awake holds. That is not a guarantee that a disconnected node can obtain other people's signatures or propagate its result.

## Local queue: exact limits, no hidden approvals

An unsigned local intent contains the desired operation and scope, clearly marked "waiting on this device". It may be validated/redrafted automatically online before the **existing** approval step; it cannot approve itself, grant membership or trigger repeated person prompts. Prefer this path when offline so a person is not asked to sign bytes that cannot yet be admitted.

Already-signed acts, subject acceptances and certificates retain their exact bytes, epoch, `prev`, nonce, expiry and evidence. There is no expiry extension, signature rewriting, automatic re-signing of person bytes or reinterpretation under a new charter. `Act::new` normally gives an hour; `GovPool::new_act` gives a week for specified multi-signer cases. These are admission windows, not permission to bypass a hold. The finalizer must distinguish an act it already durably admitted from a previously unadmitted local queue item; a known committed receipt can be returned idempotently, but late admission cannot use an old history/import path to evade expiry.

Online replay rechecks exact current eligibility, grants, charter context, issuer revocations, target state, evidence, limits and request lifetime. If the exact signed operation expired, changed context, lost eligibility or missed its cancellation window, it refuses plainly. It does not ask the person again automatically. Completing a newly necessary approval would be a new explicit request, not a promise of transparent queue completion. The queue is bounded by existing pending/request/act/evidence caps and can be discarded without changing pool authority.

An operation queued locally does not start the finalizer's hold, stop its clock, cancel another operation or reserve a decision. If the computer is merely unreachable but still running, already-admitted work may finish there. If it sleeps or its protected service stops, its awake holds stop earning time. These cases must not be conflated in UI text.

## Canonical authority and receipts

A proposed new charter format pins `FinalizerIntent {v, finalizer_id, public, device_cert_fp, owner_account_id, person_id, policy_digest, clock_policy_digest, generation}`. IDs/digests are fixed-width lowercase hex; the dedicated Ed25519 public key is canonical, nonweak and torsion-free. The Person ID is already admitted. Generation starts at one. Pool ID is 32 hex digits and the full founding anchor is 64; every signed message binds both. Genesis pin plus the complete verified founding state is committed before the signed genesis receipt. That receipt is required before a Native pool starts serving.

One strict, bounded canonical `AuthorityReceipt` chain covers every acknowledged mutation, including admitted votes/readiness/cancel/veto, not merely applied charter changes. Its header commits version/domain, pool/anchor, generation, checked sequence counter, exact parent receipt, pre-state hash, typed event and exact semantic act IDs, post-state hash, revocation commitment, and clock/hold attestations. The signature is detached from receipt identity. Genesis is sequence zero; each later record advances exactly one. Unknown/duplicate fields, malformed encodings, gaps, overflow and mixed formats refuse. No generic recursive field stripping is allowed.

The public state projection commits charter/selected history; roster, delegates, device removals and log cuts; immutable person/key/issuer bindings; active issuers/tombstones/signed cuts; pending acts and exact vote/evidence digests; readiness and its policy reference; cancellation/veto/dispute; consumed request hashes; and finalizer generation/terminal status. Typed evidence excluded from semantic act IDs is still committed by its verified evidence digest. A durable cancel/veto acknowledgment is itself a signed receipt. An apply consumes that exact public prefix; a published cancellation cannot vanish in a private mutable journal.

The protected holder independently verifies the existing signatures, distinct-person quorum, precise subject acceptance, current assurance, cancellation/dispute, removal/Recovery/founder/survivor rules and holds. Automatic serialization adds no person prompt and grants no vote. All governance entry points must require the same receipt path; a peer's unsigned `settled` or local applied cache never replaces it.

A fresh current-head quote binds the exact request digest, caller random nonce, helper challenge, daemon-incarnation nonce, pool/anchor, generation, current sequence/receipt/state hash and bounded lifetime. Clients measure their request lifetime monotonically; the holder checks its own challenge lifetime and exact current head/CAS. A restart changes the incarnation, invalidating old challenges. History signatures prove history only, never that a cached head is current. Live same-head mutation nonces cannot be evicted while valid; expired/old-head replay may return a stored historical result but cannot mutate authority. Capacity exhaustion refuses rather than weakening replay rules.

## Holds and crash-safe publication

Routine events do not invalidate an admin hold merely by advancing the receipt head. Retention requires the identical signed charter epoch/`prev`, identical act semantics and currently valid quorum. Current eligibility and cancellation state are checked again at apply. Losing quorum atomically clears readiness; reacquiring it begins a new hold. No stale privileged ready stamp is restored. Each held applied act has exactly one attestation referencing its prior signed ready receipt and exact policy; checked `ready + required <= applied_awake` must hold, with no missing/extra IDs.

Only the protected holder's checked monotonic awake running time earns hold credit. Wall time, suspend and service-off time do not. Durable checkpoints preserve earned time; restart resumes the durable counter without inferring downtime. A crash may lose unsaved credit and delay a hold, never accelerate it. The remote clock statement is administrative trust in this computer, not an independently measured hardware fact. Actual OS suspend/reboot behavior remains to be verified before activation.

The protected store implements one exclusive per-pool durable CAS over generation, sequence, parent and state hash:

1. Reopen/validate the protected store and full required prefix; reconstruct and authorize the exact transition.
2. Durably reserve `PREPARED`: exact receipt body, post-state, evidence digests, clock checkpoint, request nonce and terminal flag. This fixes the only body that can use the next sequence.
3. Sign only that reserved body inside the protected transaction; no signature, response or log escapes to a caller.
4. Atomically durably `COMMIT` signature, post-state, new head and nonce consumption. Publish the receipt only afterward.

A crash before reservation publishes nothing. A prepared reservation resumes only the identical body; a crash after signing may re-sign only those same bytes. A committed retry returns the stored identical receipt. Same nonce with different request refuses. Any uncertain write, signature/store mismatch, missing key/store or unverifiable outcome refuses. There is no initialization from a caller's receipt/cache and no supported consistent-snapshot rollback. Storage and OS durability guarantees need implementation-specific validation; this text is not a claim that a particular database already provides them.

## Transfer, recovery and implementation boundary

A planned transfer is an explicit current-quorum, held governance operation with physical enrollment of the successor's exact key/account/device/policy. Its signed terms dispose of other pending operations explicitly; private queue/timer/key state is not copied. The old computer durably commits a **terminal** receipt naming the successor, generation plus one, exact public state/head/revocations and initialization nonce before publication. Afterward it returns only that terminal record: no fresh current-head quotes or old-authority receipts.

The successor verifies the complete prior-generation public chain and exact terminal scope, not just one signature. It initializes once with its own enrolled key, starts the next generation at sequence zero linked to the terminal receipt, and preserves the exact public state/revocations. Transfer uses the same prepared/committed crash ordering. No node may simply switch its current key while the old service remains active.

A missing/offline old holder cannot be fenced by a replacement's self-claim, an unsigned tombstone, a timeout election or quorum alone. No lost-holder recovery is authorized here. Re-founding a new pool, or separately accepted physical destruction/external fencing, is a separate explicit recovery contract. Neither silently replaces the original pool or moves its private state.

Proposed implementation map, only after availability approval and exact source review: `poolhouse-authority` for canonical receipt/quote and protected-store transition interfaces; a protected installed holder for exclusive durable CAS/signing/clock/terminal lifecycle; node `gov/{act,body,charter,chain,pool,roster,ops}` for receipt-based application and exact eligibility; `gov/phone_verify` and trusted Native approval surfaces for existing scoped person approval; `poolapi`/network ingestion for local queue and receipt routing. Native certificate signature verification stays separate from active issuer/person eligibility. Android current attestation/publisher/revocation checks must remain fail-closed; a declared Strong field is never sufficient.

Required validation includes all ten attack categories, crash injection at every publication boundary, cancellation/apply ordering, lost-quorum hold reset, clock suspend/reboot, duplicate/expired nonce and stale-head replay, transfer before/after terminal, copied pools/keys/state, current issuer revocation, Recovery and joint-removal guards, all routine journeys above, and no extra signing prompt. Actual OS/root custody, protected approval focus/password/no-reuse, durable storage and hardware workflow proof remain unfinished.

The unresolved product decision is whether the waits/refusals above are acceptable for a Native-capable phase-0 pool. Local queueing preserves work but does not preserve offline membership, cancellation or revocation authority. No implementation should describe that tradeoff as "only sensitive actions wait".
