# macOS worker confinement: supported mechanisms and remaining proofs

Research date: 2026-10-23. This is documentation feasibility, not execution evidence or an accepted architecture. No builds, probes, installations, OS-log inspection or product API calls were performed. The existing strict-launch failures remain failures; none of these sources establishes that the proposed worker already runs.

## Separate capabilities require the appropriate launch boundary

Apple's current guidance distinguishes direct children from independently configured helpers. A sandboxed app launching a helper through `Process` or fork/exec gives that helper the launching app's sandbox capabilities. For distinct capability subsets, Apple identifies an XPC service, a login item, or a background helper application. Therefore a network-capable node's ordinary inherited helper is not, by inheritance alone, a narrower no-network worker. This is a constraint on design selection, not a tested result. [Discovering and diagnosing app sandbox violations](https://developer.apple.com/documentation/security/discovering-and-diagnosing-app-sandbox-violations).

The supported embedded command-line helper pattern signs the helper with just `com.apple.security.app-sandbox` and `com.apple.security.inherit`. Apple's current packaging guide warns that other entitlements can cause immediate launch errors; specifically, Xcode's injected `get-task-allow` is incompatible with inheritance. Those are developer packaging requirements to automate, not setup steps to give a library user. The guide also covers Developer ID distribution, not only app store delivery. [Embedding a command-line tool in a sandboxed app](https://developer.apple.com/documentation/xcode/embedding-a-helper-tool-in-a-sandboxed-app).

Apple's archived entitlement reference separately configures each app/XPC target. An inherited child obtains static entitlement permissions, but not the parent's dynamic post-launch PowerBox file grants. It recommends passing file data or a bookmark for such files. An inherit-entitled helper must not be treated as a separately launchable standalone sandbox with its own independently chosen capabilities. [Enabling app sandbox](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html); [current Apple DTS standalone-helper clarification](https://developer.apple.com/forums/thread/818202).

## Descriptor capabilities and filesystem access

An inherited open descriptor is already authority: Apple's secure-coding guidance explicitly treats open files, sockets and shared memory inherited across fork as capabilities, and instructs developers to close unnecessary descriptors or use close-on-exec. A design with directional handles must therefore give the worker only the read/write ends and access modes it needs, close the opposite ends, and exclude inherited network/control sockets. This last sentence is a design inference, not a promise that sandbox entitlements revoke an inherited descriptor. [Elevating Privileges Safely](https://developer.apple.com/library/archive/documentation/Security/Conceptual/SecureCodingGuide/Articles/AccessControl.html).

Public XPC supports transporting descriptors: `xpc_fd_create` duplicates the supplied descriptor, and `xpc_fd_dup` obtains an equivalent descriptor on receipt. This is a supported alternative for explicit handle transfer, but documentation of descriptor transport does not prove application-specific directionality, peer identity, revocation, filesystem scope or worker confinement. Those properties still need contract review and actual packaged-worker tests. [xpc_fd_create](https://developer.apple.com/documentation/xpc/xpc_fd_create(_:)).

For a worker that needs no network, independently configured app sandbox omits the client and server network entitlements; those keys respectively permit outgoing and incoming socket connections. Omitting them is not proof of zero communication through inherited handles or permitted system services. Similarly, user-selected file access/bookmarks are explicit access-grant mechanisms, not an excuse to request broad model-directory access from each user when the product can deliver authorized data or appropriately restricted descriptors internally. [Security entitlements](https://developer.apple.com/documentation/bundleresources/security-entitlements); [Enabling app sandbox](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html).

## Launch and service identity constraints

Apple's archived XPC lifecycle guide describes services bundled in the containing app, launched on demand by launchd, restarted after crashes, and eligible for termination when idle. It explicitly does not support elevating an XPC service to root. Consequently a bundled per-user XPC helper must not be asserted to provide a dedicated service UID, before-login availability, persistent worker lifetime or cross-user service simply because it has an independent sandbox. [Creating XPC Services](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingXPCServices.html).

For macOS 13+, `SMAppService` is Apple's public app-bundled mechanism for login items, launch agents and launch daemons; it also exposes service status and a native System Settings destination. Login items/agents are login-scoped. A registered LaunchDaemon is not bootstrapped until administrator approval and, after approval, is bootstrapped on subsequent boots. Product code can register and explain status through native UI; general task authorization cannot substitute for required OS approval. This establishes a supported lifecycle avenue without terminal commands, not proof that a dedicated account is created, that its storage is usable, or that this project's protected install has been implemented. [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice); [register](https://developer.apple.com/documentation/servicemanagement/smappservice/register()).

App/group containers concern storage sharing, not service identity. Current Apple guidance notes that macOS 15+ protects app-group containers and that access by an app outside the group can trigger user authorization. A proposed dedicated service UID's container ownership, startup access, entitlement/signing membership and interaction with protected model storage remain unresolved implementation/proof requirements. [Protecting local app data using containers on macOS](https://developer.apple.com/documentation/xcode/protecting-local-app-data-using-containers).

## Hardened runtime and engine compatibility

Hardened runtime protects code execution and enables library validation by default; it does not replace app sandbox resource restrictions. Apple permits Apple-signed libraries or libraries with the executable's Team ID. Bundled native dependencies therefore need compatible signing; this research supplies no reason to disable library validation. [Disable Library Validation entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation).

CPU JIT using writable/executable `MAP_JIT` memory requires the narrow `com.apple.security.cs.allow-jit` exception under hardened runtime. Broader unsigned executable memory or executable-page exceptions must not be inferred from a dependency's name. MLX's own build defines `MLX_METAL_JIT` as compilation of Metal kernels, default off; its installation documentation describes runtime GPU kernel compilation and caching. That is not evidence of a CPU `MAP_JIT` requirement. The actual linked engine, Metal compiler/cache paths and signed dependencies still require a reviewed entitlement inventory and packaged-hardware verification; none was executed here. [Apple JIT entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-jit); [MLX build](https://github.com/ml-explore/mlx/blob/main/CMakeLists.txt); [MLX installation](https://github.com/ml-explore/mlx/blob/main/docs/src/install.rst).

## Why the experimental custom-profile launcher is not the product route

The installed public Xcode SDK's `usr/include/sandbox.h`, lines 7–9, directs developers to app sandbox. Lines 32–33 require `SANDBOX_NAMED` and reserve all other flag values; line 45 marks `sandbox_init` deprecated and no longer supported. A custom SBPL string with flags zero is not a documented supported public contract. These SDK observations do not diagnose the preserved experimental `sandbox-exec` SIGABRT. Its failures and the separately labelled unconfined ABI baseline remain unchanged; neither establishes worker confinement. See [ABI evidence](native-macos-ipc-abi-evidence.md).

## Bounded conclusion for the integration owner

The public supported route worth evaluating is a signed app sandbox helper with an independently chosen capability set and an appropriate system-managed launch boundary, with explicit restricted handle delivery. An inherited helper is useful only when inheriting its parent's full static sandbox is acceptable. Selection among XPC, background helper and service-managed components remains a common-contract decision; this research does not authorize an adapter, change shared schemas, or establish H/K/P/VerifiedSender acceptance. Dedicated identity/protected install, before-login launch, actual no-network behavior, precise handle closure, filesystem access, engine/Metal compatibility and lifecycle cancellation still need reviewed implementation and installed-hardware evidence.

The intended normal journey is application-managed packaging, registration, launch, handle delivery and recovery, with native status/approval UI only when macOS requires it. It introduces no terminal command, custom profile, copied token, manual claim or recurring permission ceremony for a library consumer. Protected service installation, dedicated UID provisioning, startup before login, signed worker/engine compatibility and actual directional-handle confinement remain unfinished proofs; this note does not select or implement their adapter.
