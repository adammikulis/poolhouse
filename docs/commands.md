# The commands

Every command is installed as `poolhouse-<command>` and answers as `poolhouse <command>` too;
both spellings run the same code, so `poolhouse-serve status` and `poolhouse serve status` are one
command.

| | |
| --- | --- |
| `poolhouse-models find <words>` | search the Hub for a model, unsloth first; `files <repo>` lists the quantisations and prints the `hf:` reference to serve each; `card <repo>` reads the sampler settings its publisher recommends; `layout <model>` prints the attention layout off a GGUF header -- which layers hold a full cache, slide, recur or share it, plus experts, indexers and lookup tables |
| `poolhouse-models migrate plan\|run` | move the old `<state>/models/<owner>/<repo>` store into the Hugging Face hub cache, where every download now goes: `plan` counts files and bytes without hashing, says whether the move is a link on one volume or a copy, and names what blocks it (a model server holding a file, an unwritable cache); `run` checks each file's size and digest against the Hub's listing, links it into `blobs/` and `snapshots/<commit>/`, removes the old path after the link reads back, verifies and deduplicates against a blob the cache already has and never replaces one, leaves what the Hub cannot vouch for in place and lists it (exit 1), and appends to `models-migrate.log` |
| `poolhouse-models adopt plan\|run [--offline]` | take the models kept outside the Hugging Face hub cache into it, so every tool shares one copy: the decider's pinned files (`<cache>/decide/snapshots`), the weights views (`<cache>/spec/weights`, whose names stay) and the quantized drafters (`<cache>/spec/dflash`, `<cache>/spec/mtp`, filed in the cache as `poolhouse-derived/<owner>.<repo>.<recipe>` with a `provenance.json` naming the source repository, commit and recipe). Every file is vouched for first, by the Hub's listing, else by the record its download left, else (a weights file) by its structure, and linked on the cache's volume, never copied, so `plan` shows 0 B of extra disk. A file the cache already holds is compared byte for byte before its twin is removed, and a file nothing vouches for stays where it is and is listed (exit 1); `run` appends to `models-adopt.log` and a cut-off run is finished by the next |
| `poolhouse-serve fit` | how many people fit at a given context, and the longest context one person can have -- from **measured** per-model KV numbers, not a formula: `--measure` serves a model once at `-lv 4` and records what llama.cpp says it allocated; `--room 24G` asks about a machine that is not this one; `--per-user N` sets the contexts in the table; `--plot FILE.png` draws who fits against the context and what the memory costs as the users arrive, with the familiar card sizes behind it, so a large model with a tiny cache can be seen overtaking a small one with a fat cache; `--write FILE` writes the Markdown; `--ui` puts the same two panels up as an interactive page on loopback (also the app's **Fit** view) |
| `poolhouse-serve limits [--memory 90G] [--servers N] [--slots N] [--idle 10m]` | how much of this machine poolhouse may take, written down once and read everywhere: the memory cap rides on `hub.room`, so every preflight, fit and lease honours it without being handed it; the server and slot caps refuse a lease **before** a process is started, naming what to stop or what to raise; `--idle` is what `reclaim` and the fleet daemon act on. Every limit is off until one is set, so a machine nobody has told anything about behaves exactly as it did; `--clear` takes them all off |
| `poolhouse-serve reclaim [--idle 10m] [--watch]` | stop the model servers nobody is using, so the memory they hold goes back. Idleness is **asked** of each server (`/slots`) rather than remembered, since a written-down 'last used' is only as good as every caller remembering to write it and an adopted server has no caller here at all; a server that does not answer is left alone, and a long single answer is never mistaken for idleness. What each look found is kept, so idleness adds up across looks and a pass can act on what the daemon has been watching -- but only over intervals short enough to be an observation: a gap in the looking is a gap in the evidence, and a pass after a silent afternoon reports nearly nothing and stops nothing |
| `poolhouse-serve status\|up\|down\|profile\|build\|escalate\|memory` | one model per port, in one shape; refuses a mismatched lease; announces to the fleet; `--draft auto` and `--mmproj auto` find the speculative head and the vision projector shipped with the weights; `--spec` chooses draft or n-gram guessing; every start writes the server's own output to a log of its own under `~/.poolhouse/logs` (the last five per port are kept); `status` names that log, the head each running server was started with and the share of its guesses the model is keeping, and with nothing serving, the log the last server on the port wrote; `profile` prints the shape a model measured best in for each workload -- asking, ingesting or chatting -- and `up --profile --workload WORKLOAD` fills every flag not given from that record; `build` compiles or downloads a current llama-server and switches to it once verified, so a release lagging master by an architecture is a permanent fix rather than a one-off `--binary`; `escalate --add N` grows a running server's slots in place, carrying its conversations over; `memory` says how much a model may use here and `--persist` makes that survive a reboot |
| `poolhouse-serve leases\|history [--model NAME] [--since 3d]` | every lease records why it was taken (`up --for TEXT`, `$POOLHOUSE_LEASE_FOR`, or the program's own reason), who took it, the process chain that started it, its working directory, git worktree and branch; `leases` lists each server's holders with all of it, `status` shows it beside each lease and names the other holders of an adopted server, and `history` lists the leases that have ended |
| `poolhouse-claude [MODEL] [--role R] [-- claude args]` | Claude Code on a model this machine serves (default Qwen3.8-27B-UD-Q4_K_XL, 262,144 tokens on one slot, q8_0 KV cache): the lease is taken, every model variable names the served alias, the window and auto-compact size are set to what is served, telemetry and betas a local server lacks are off, and the server goes when claude exits. A PreToolUse hook sends every tool call through the destructive-action classifier under the role (`read-only`, `approve-first`, `plan-and-go`) and asks in the Requests inbox; the settings file sits outside the working tree. The session is registered on the project's board as a subagent of the session that starts it, and retired on exit. `--on URL` talks to a server as it stands; the served model's own chat template is rewritten first |
| `poolhouse-codex [MODEL] [--role R] [-- codex args]` | Codex on a model this machine serves, the default coding harness: the same lease, window, permission hook and workspace session as `poolhouse-claude`, with a private `CODEX_HOME` holding the provider (`/v1/responses`), the context window, the selected permissions and Plan or Execute mode and the hook. `launch_coding_agent(model, policy, project, harness)` in `poolhouse.coding` is the same for a program |
| `poolhouse-agent "task" --model MODEL` | one agentic task through the Claude Agent SDK (the `claude` extra) on the same lease; prints what it said and what it spent. `poolhouse.harness.session()` is the same for a program |
| `poolhouse-features list\|enable NAME\|disable NAME` | the experimental features, each off until turned on for this machine: `list` shows every one with its stage (`experimental`, `beta` or `stable`), what it does and what it risks (`--json` for a program); `enable` and `disable` change one by name and record who did it in the authority audit log. The state is the `features` map in the daemon's `settings.json`, so the settings screen shows the same list. A safety floor (pushing to main, an agent posing as a person, the keystore, sharing the GPU) is never a feature and is refused. `--root DIR` names a daemon kept elsewhere |
| `poolhouse-store check\|docs\|doc\|embed\|tidy` | what a graph store holds and whether it agrees with itself: `check` reads every document, node and edge by key and by scan and prints each disagreement (`--fix` rewrites a document a scan reads empty), `docs` lists the documents with their sizes, `doc PATH KEY` prints one as JSON (`--drop` takes it out), `embed --smooth N` spreads the vectors the store already holds over the graph so an entry with no text of its own is found by what its neighbours mean, and `tidy` runs the hygiene pass -- duplicates merged, inverses folded, doubtful labels flagged, conflicts, orphans and hierarchy cycles reported -- dry unless `--apply`; `--base-url URL` has a served model judge the names a spelling apart, the verbs in conflict and the doubtful labels from their passages, every verdict written to the store, `--rejudge` asks about every held verdict again, and `--gold` scores the judge against cases whose answers are known; `embed` and `tidy` are offered by a build that holds `poolhouse.graph.smoothing` and `poolhouse.graph.tidy`, and a build without them lists only `check`, `docs` and `doc` |
| `poolhouse-security status\|events\|quarantine\|review\|scan\|baseline\|verify\|downloads\|hosts\|scanners\|sandbox\|unlock\|keystore\|keystore-reset` | what sentinel has seen and holds, each listing JSON with `--json`: `status` is the mode, counts by state, pins, decoys and whether the event log's hash chain verifies, and names what is held with the command that reviews it (`chip` is the same as a green, yellow, red or none mark); `review` is one screen of everything held with the reason in plain words, what it blocks and single keys to release one (`r`, `y`), stop watching every watched item (`R`), see details (`d`) or purge (`p`, id typed), for a person at a terminal; with no terminal it shows one dialog listing what is held with `Release`, `Keep held` and `Later` buttons, and `review --list\|--json` prints it anywhere; a quarantine that means something changed or was forged raises at most one such dialog at a time on the machine (everything held is in it, `Release` releases exactly what it lists), and anything else is shown by `status` and `chip` only; `POOLHOUSE_NOTIFY=off` shows no dialog; `events` reads the log; `quarantine list\|show ID\|add KIND:KEY` covers every kind of subject (messages, tool calls, tools, sessions, memory, models, artifacts, servers, MCP servers, credentials, members) and `release ID`, `purge ID` and `mode` need a person at a terminal who types the id, and refuse when an agent started the process; `scan [--deep]` re-hashes every pinned file and checks the decoys, `baseline --pin FILE [--honey]` pins a file by digest and plants the decoys, `verify [--anchor LINE]` checks the log for edits, cuts and reordering; `downloads [--held] [--verify]` lists what came in from the internet with its source, hash and scan status, `hosts` and `approve-host HOST` show and extend the hosts that may be reached, `scanners` says which virus scanners this machine has, `scan-policy [CATEGORY ACTION]` shows or sets whether files nobody could scan are kept (the last two changes need a person at a terminal); `sandbox status\|test` names the backend that confines untrusted execution (and the deprecated tool behind it) and runs its guarantees against real confined processes, exit 1 when one fails `unlock` (a person at a terminal) makes the keystore's one master key and lets background processes read it, `keystore` prints whether it exists, any refusal and the operations this hour without touching the keystore, `keystore-reset` deletes it (docs/keystore.md) |
| `poolhouse-jobs status\|wait KIND\|stop KIND` | the long commands this machine has recorded -- a detached bench sweep, an ingest reading documents -- with the pid, the argv and the log of each: what is running, blocking until one has ended so the next command is `wait && next` rather than a `pgrep` loop written by hand, and ending one |
| `poolhouse-test-devices [DEVICE] [--json]` | the other devices of this node's pool, whether each takes tests, and what this project last showed there: platform (a WSL Linux is named as WSL, apart from the Windows around it), Python, free test slots out of two, and the last result. `scripts/test TIER [FILE...]` with its --on DEVICE|all and --split options runs the same tier on them: the receiving node unpacks this working tree (uncommitted edits travel), runs `scripts/test` on its own Python 3.13 under its lease service and sends the result back in the shape of a local run; a file that passed on a device with the same content, platform and tier is not sent again, and a pass on one device never satisfies another. Both ends are off until a person turns them on: the experimental feature `remote-tests` (`poolhouse features enable remote-tests`) on each machine, and at the device that runs the tests `python -m poolhouse.testfarm.consent on` naming the sending device with its --from option (audited on the pool board; it takes tests only from the devices it names, and being in the pool is not enough); `off` stops the next upload (docs/test-farm.md) |
| `poolhouse-workspace send\|inbox\|watch\|notes-add\|scratch-new\|claim\|grants\|status` | how the agent sessions of a project coordinate through the node of their device, without a person relaying text or sharing scratch files: a harness hook registers each session (a subagent is registered by the session that starts it, `spawn`), the node names it and records its parent, and every message, note and claim is attributed from its token, never from what it says; nobody mints or copies a token. `doctor` checks the session that runs it, `status` shows who is registered, `hello` sends a first message, `snippet` prints the paste block for an agent that starts without a hook, and `hook-snippet` and `install-hooks` set the nudge hooks. `send` / `inbox` / `wait` / `watch --once` are a durable ordered bus (a lead starts `watch --once` in the background and its exit is the wake-up); `board`, `dm`, `subscribe` and `digest` are the rooms and what reaches an inbox; `notes-add\|notes-search\|notes-get\|notes-verify` keep decisions, rules, facts and questions with a trust level the node sets (test-verified by an allow-listed re-derive command, agent-claimed) and a TTL after which they are stale; `scratch-new\|-ls\|-path\|-rm` give each main session an owner-only folder that refuses paths outside it; `attach` and `file` share a file by handle; `claim\|release\|heartbeat\|who\|claims` own branches, worktrees, ports, source areas, install environments and servers until the TTL or the owning pid ends; `land-review` records a review of a branch's exact commit (an accept is advice, a reject stops a push of that commit); `task-create`, `tasks` and the other `task-*` commands run the board's tasks on the node; `agent start\|stop\|list` runs a local model as a session of its own; `quarantine-ls`, `quarantine-release` and `status` (with the test-slot queue) are read or person-only. `approval request ACTION[:RESOURCE]... [--for 10m] [--uses N] [--note TEXT] [--wait SECONDS]` asks the person's phone for one to eight grants for the session and prints the handle and the plain-words text the node wrote (the same request made again is the same item, and a request that is not routine also prints the number to show the person, who chooses it among three after their fingerprint), `approval status|wait|cancel|list|pending` read what became of a request (`wait` is `pending` when its time runs out, which is not a failure), and `approval decide ID approve|deny|block` is a person's at a terminal: the other signer of a request, after a typed yes; `phone add` is a person's at a terminal and shows the code a phone scans (the whole of a first phone's setup), `phone offer` makes a link for one more phone once one is added, `phone list` shows the phones and `phone remove NAME` is a person's (docs/phone-approval.md); `grants` and `grant-log` show who holds which standing grant, when it ends, how often it was used and every issue, revocation and use; `grant`, `revoke-grant`, `grants-setup`, `person-proof`, `person-enroll`, `person-unenroll` and `rebind` are a person's at a terminal: each shows what it will sign and signs with the person's key only after the person types yes on the terminal device, and the node counts a grant only when an enrolled person key signed it; `rebind HARNESS SESSION` moves a main session to the terminal it runs in (the node registers a main session again, and lets a token spend a grant, only from the process lineage it was registered from); what the typed yes and the lineage do not stop is in the Standing grants and Identity sections of docs/node.md. Everything read back is fenced as untrusted data from an agent and carries no authority; writes holding a credential or a term from the private-terms denylist are refused; `--json` on most commands |
| `poolhouse-speech providers\|transcribe\|say\|regions` | what this machine can hear and say: `providers` lists every engine -- faster-whisper, whisper.cpp, Whisper through transformers, piper, kokoro, the operating system's own voice, Silero and an energy detector that needs nothing installed -- with whether it could run here and which one is picked when none is named; `transcribe FILE` prints the text (`--json` the segments with their times), `say TEXT --out FILE.wav` writes the spoken line, and `regions FILE` the seconds somebody is speaking. `--provider NAME` picks one engine, `--language xx` names the language rather than guessing it. Audio is anything ffmpeg reads |
| `poolhouse-credentials set\|list\|unset\|path` | the tokens and keys the stack reads, found in this order: the environment variable `NAME`, the file `NAME_FILE` names (a mounted secret), the credentials file `~/.poolhouse/credentials.toml` (`POOLHOUSE_CREDENTIALS_FILE` moves it), Hugging Face's own token file for `HF_TOKEN`, and the values stored with `--keychain`, wrapped under the keystore master key (docs/keystore.md); `set NAME` reads the value from a hidden prompt or stdin (never an argument) and writes the file atomically, mode 0600; `list` prints each name with where it comes from and never a value; a credentials file other users can read is refused until `chmod 600` |
| `poolhouse-setup` | what this machine can do — memory a model may use and whether that survives a reboot, which architectures the installed build reads and how old it is, what is already downloaded, what speech providers answer — and what the stack does without being asked; `--checkouts` adds everything `poolhouse-doctor` checks on its own, in the same command; `--yes` runs the fixes offered; exit 1 when anything is wrong |
| `poolhouse-doctor` | the checkouts (hooks installed, working tree clean, how far ahead of origin, a worktree pinned behind HEAD, whether `import poolhouse` lands in the checkout or a copy), the bench store (runs that read back as nothing, a `measuring.json` whose pid is dead, a log with no run kept from it) and the managed llama.cpp (`current` answers `--help`, the named builds, one older than 14 days) — the checks `poolhouse-setup` leaves for a second command; `--repo PATH` or `$POOLHOUSE_CHECKOUTS` (none by default) picks the checkouts, `--bench-home PATH` the store, `--yes` runs the fixes it offers; exit 1 when anything is wrong, and never a push |
| `poolhouse runtime ensure\|status\|rollback\|restart-host` | the installed runtime follows the source checkout without waiting for the machine to be idle: ensure builds the checkout's HEAD from a `git archive` into a new immutable tree beside the old ones, smokes it (import in isolated mode, the stamped commit, the workspace CLI help, the Claude hooks against a temporary state root), rewrites every console launcher atomically and selects it; a failed build or smoke leaves the selected runtime alone and is recorded; a selection that is missing, unimportable or below the epoch in packaging/runtime-floor falls back to the newest verified runtime and rebuilds; the background option returns at once, and one build runs at a time under an install claim held by the acting workspace agent; status lists the selected, kept and unmanaged runtimes; rollback selects the newest earlier runtime and holds the commit it left until HEAD moves; restart-host replaces the running host (the daemon Poolhouse starts) with one on the selected runtime through the job-preserving restart, keeping its port and root, and never signals a process; the checkout, launcher directory, ref and force options override what is recorded. An agent runs ensure, rollback and restart-host only while the owner has delegated the `runtime.deploy` gate (`poolhouse-workspace authority show`); the Dev preset delegates it, Prod keeps it with the person |
| `poolhouse-decide ask\|eval\|calibrate\|bench\|train\|jevbench` | a decision model picks one of a named set of options and reports a probability for each: `ask QUESTION --state TEXT --option NAME[=DESCRIPTION]` answers one, `ask --state TEXT --noul NAME=Q --choice NAME=Q:A,B --score NAME=Q:LO..HI [--json]` answers several named yes/no, choice and ordinal-score questions about one state with probabilities (`p_true`, per-option, expected value; a failed question abstains with an error and the command exits 1), `eval CASES` and `bench CASES` score backends (`pointer`, `logprob`, `embed`, `rules`) on a JSONL file of labelled cases or on `guards`, the built-in agent-guard set, for accuracy, Brier score, expected calibration error and latency percentiles, and `calibrate CASES --out FILE` fits temperature scaling (and `--isotonic`) on whole groups held apart from the scoring; `export-cases`, `make-cases TOOLS.json` and `check-cases` write, synthesise and read the case format, `list` shows the trained deciders, `fetch --yes` downloads the pinned pointer checkpoint, `train` fine-tunes a decider from labelled cases (`docs/decision-models.md`) and `jevbench` scores the backends on the public JevBench items (opt-in, uses the GPU) |
| `poolhouse-pool join\|status\|list\|leave` | one command makes this machine a member: the checks serving depends on, a llama-server if there is none, the passphrase, the daemon (`--persist` starts it at logon too), and then the devices in the pool; `status` lists every member with what it serves, its room, whether it is measuring, the commit it runs and how it updates itself; `leave` undoes it; `--track main` makes this machine follow a branch rather than releases |
| `poolhouse-pool add-device\|requests\|accept\|decline\|nearby\|join-with-code\|remove\|bootstrap\|share\|fetch\|signing\|model-sources\|devices` | put a new machine in the pool without downloading anything by hand, and without anyone pushing anything at it: `add-device` opens this machine to a join for a while and asks you with a dialog whose buttons are Decline, Accept as mine and Accept as someone else's (a second dialog then shows a six digit code; `POOLHOUSE_NOTIFY=console` prints instead, and `accept ID --mine\|--other` / `decline ID` answer from the terminal); the new machine runs `join-with-code --host H` and types the code -- a password-authenticated exchange (the `spake2` package) that fails for a wrong code (three tries) or a machine in the middle, then hands over the pool key unless `--no-pool`; `nearby` lists machines open to joining; `remove` takes a member out of the pool; `share --dir D` serves files, signed, with a level per file (open, owner for a gated model that only your own devices get once your licence acceptance is recorded, never) and `fetch NAME --from H:P` brings one into staging; `model-sources` lists, adds, removes or switches off (`off`/`on`) the members that `poolhouse-models pull` and `fetch` ask for a model file before the Hub (the `no-members` option of those commands or `POOLHOUSE_NO_MEMBERS=1` skips them; docs/model-discovery.md); `signing` shows the signing key (kept in the OS keystore) and does export, rotate, revoke and confirm-before-signing only for a person at a terminal; `devices` shows each member as lan, tailnet or unreachable and whether Tailscale was found (read-only `tailscale status --json`; a tailnet is a route, the pinned certificate still decides; `--learn` stores a tailnet address only after the certificate matched there); `bootstrap --share DIR` offers the wheel on the LAN for ten minutes to a machine with nothing installed, and `bootstrap --ssh [user@]host --share DIR [--dry-run]` installs over your own ssh keys with a host key typed in full and a fixed script that checks an OpenSSH signature and every SHA-256 first. Everything takes `--json`; docs/onboarding.md has the design and what is not built |
| `poolhouse-device pause\|resume\|schedule [busy HOURS\|free HOURS\|clear]` | control one selected device, this one by default or `--name NAME`: `pause` stops taking new work and follows that device's configured stop/leave policy for running jobs, `resume` starts admission again, and `schedule` shows its hours. `schedule busy 'mon-fri 09:00-17:00'` adds busy hours, `schedule free HOURS` carves out an exception, and `schedule clear` removes the windows. Pool-wide pause/resume remain under `poolhouse pool` |
| `poolhouse-device-setup [--yes] [--dry-run] [--wait SECONDS]` | set this device up to join a pool, the same one command on macOS, Linux, Windows and WSL: it lists every change the device needs, asks one yes (`--yes` for an agent or script that is already allowed), makes them (inbound firewall rules by port on Windows and WSL, mirrored networking for WSL, the node started with its network on) and ends with READY, or NOT READY and the one fix; `--dry-run` only lists them |
| `poolhouse-mcp` | the same functions, as MCP tools over stdio for an agent to drive -- `serve_*`, `models_*`, `fleet_*`, `speech_*`, `setup_look`, `doctor`; anything long detaches and returns its log and pid; `--list` prints the tools |
| `poolhouse <command>` | runs any `poolhouse-<command>` listed here (`poolhouse chat ...`, `poolhouse serve status`, `poolhouse train run ...`); `--list` prints each with the first line of its help; bare, the daemon and your browser on it |
| `poolhouse-graph geocode --graph FILE --cache FILE.json` | every entry that names a place given a point through Nominatim, cached so a place is asked about once, written back onto the node as `lat`/`lon` -- which is what the page's map draws. `--near K` joins each placed entry to its K closest with a `near` edge weighted 1/(1+km), `--out` writes elsewhere than over the graph |
| `poolhouse-graph serve --site FILE` | a rendered graph page (`graph.page.render`) served on loopback as a whole document: `GET /` is the page with `window.GRAPH_LIVE` set so it asks this server rather than nothing, `/export/<path>` a file under `--export DIR` (JSON and HTML by their suffix, anything else as bytes, nothing outside the root), and the ask routes -- `/ask`, `/ask/stream`, `/thread/<name>`, `/ask/model`, `/metrics` -- answered over `--graph FILE` (a build without `poolhouse.graph.conversation` answers `/ask` with a plain sentence that it does not answer questions about a graph) with `--model` leased on the first question (`--model-port` is where it is served), every question and answer kept in `PATH.conversations` beside the corpus `--store PATH` names, never in it (`--conversations-in-store` keeps them in it); `--port` picks the listener. `POST /request` appends the page's change request to `--requests FILE` (`PATH.requests.jsonl` beside the store, or beside `--site` without one) and has the model propose edits for it into the review queue `GET /review` lists and `POST /review` accepts, refuses or undoes (`--review FILE`, `PATH.review.json` by default), an accepted edit landing in `--store`; `/refresh` and `/draft` answer once a subclass gives them stages and a drafter |
| `poolhouse-audit` | every tracked file of a checkout read for a person's details with the pre-commit hook's reader -- names from `NAMES_GRAPH` and `NAMES_SCRAPE`, the allow-lists, the shape rules and the recogniser, asked about card numbers, IBANs and passports as well as people -- printed as a list to look at, exit 1 when there is one; `--staged` is the hook's own check without a commit, `--all` adds the noisy kinds (places, dates, URLs, addresses, driver licences), `--floor` the recogniser's confidence, `--root` another checkout, `--fixtures` the allow-list, `--json` one object per finding. `scripts/encrypted-volume.sh NAME DIR setup\|mount\|unmount` keeps a directory inside an AES-256 sparsebundle on macOS, the passphrase in the login keychain as `NAME-data`; setup with a source directory moves it in and leaves a symlink |
| `poolhouse-node permission [--seconds N] | build [--binary PATH] [--icon SVG] | key [--migrate]` | the macOS identity of the LAN node: `build` makes Poolhouse.app (bundle id `app.poolhouse.node`) under `~/.poolhouse/apps` and signs it with the local certificate `Poolhouse Local Signing`; `permission` launches it once with a short multicast probe so macOS shows its Local Network prompt, and prints GRANTED, DENIED or NOT ASKED; `key` says where the device key is kept (the keystore, a passphrase file, or a file, which is weak), and `key --migrate`, run by a person at a terminal, moves it from its file into the keystore |
| `poolhouse-memory` | what the chat agent remembers across sessions, for a person at a terminal (an agent's process is refused): `list`, `show ID`, `add TEXT` (`--kind` preference, machine, result or note; `--source`; `--model`), `confirm ID` (checked under the build in use now), `forget ID` or `forget --all`, `export` as JSON and `stats` (size, limits, facts to re-check, whether the sealed store passed its integrity check); facts about a build or a measurement are marked to re-check after the managed llama.cpp build changes or 30 to 90 days |
| `poolhouse-reputation` | how every source poolhouse deals with (host, URL, address, fleet member, model repository, artifact hash) has behaved, for a person at a terminal (an agent's process is refused): `list`, `show KIND:NAME`, `forget KIND:NAME` or `forget --all`, `export` as JSON and `stats`; a source that was reliable and changes is watched at once, and only clean runs or `forget` restore one |
| `poolhouse-log` | the per-user activity log, read-only (docs/activity-log.md): tool calls and their outcomes, questions put to the person and the answers, rule and role edits, workspace messages and claims by metadata, keystore and quarantine events, source reputation, model leases, downloads, kept bench runs and test results by tree hash; never a body. `tail` (the default, `-f` follows), `today`, `show ID`, `stats`, `related AGENT SUBJECT`, `verify` (says where the chain breaks) and `export --json FILE` (a person at a terminal only); filters `--since 2h`, `--agent`, `--kind`, `--session`, `--grep`, `--timeline` for a session as a story; `POOLHOUSE_ACTIVITY=off` stops a person's own process writing and is itself recorded |
| `poolhouse-requests` | every request that waits for a person (docs/requests.md), for a person at a terminal (an agent's process is refused): `list` (`--state`, `--agent`, `--project`, `--kind`, `--json`) shows them waiting first, `show ID` every word and choice with its fingerprint, `answer ID CHOICE` shows the request and asks for a yes (or takes `--fingerprint FP` from `show`) and is refused when the words changed since or another answer came first, `watch` prints a line when one arrives or is answered (`--once` prints the current ones and stops); `poolhouse-security status` and `chip` carry the number waiting |
| `poolhouse-chat ["TASK"]` | one agent for poolhouse, under a role: with no task a conversation (resumable with `--resume`, compacted when it fills the context), with a task in words (`"run benchmarks with quince-2b"` or `--task`) it asks what is open, shows its plan once, asks go, runs the calls that plan names and ends on `done` with a cost line. `--model` (by default the best downloaded mixture-of-experts model ranked for an agent) or `--url` for one already up. `--role read-only` offers only reads, `approve-first` (the conversation default) asks before each call that acts, `plan-and-go` (the task default) runs what the approved plan names and asks about anything else; a run that has read outside text always asks. Every question offers allow this time, always allow or never allow; `poolhouse-chat rules` and `/rules` list and edit those. Changing the role, the rules, releasing quarantine and approving a host are the person's alone (`/role NAME`) |
| `poolhouse-members setup\|init\|key\|token\|ls\|roster` | the pool this machine belongs to and who else is in it: `setup` joins one with the passphrase every machine shares (`init` mints a random key instead), `key` and `token` print the key and the bearer token it derives, `ls` lists the daemons answering on this LAN. `--pool-key` picks a key file other than `~/.poolhouse/pool.key` |
| `poolhouse-open [--print]` | open this machine's running Poolhouse page, signed in with a one-use address; `poolhouse open --print` prints it instead of opening a browser. Only a person at a terminal can obtain this address; an agent or pipe receives no ticket |
| `poolhouse-traind [--root ROOT] [--gym-python PYTHON]` | the daemon behind a member: one box, one job at a time, reachable over the LAN. `--root` selects the persistent workspace; reuse it to keep completed setup. `--gym-python` selects an existing simulator interpreter and saves it under that root, so later launches reuse its installed libraries; `POOLHOUSE_GYM_PYTHON` overrides the saved selection, otherwise the saved interpreter precedes the managed environment. It announces this machine (`--no-announce` keeps it invisible), serves the API and the web interface (`--no-web` only the API), runs `--slots` jobs at once, declares `--label` roles work can require, and reports the card through `--report MODULE:CALLABLE`. `--busy WHEN` and `--free WHEN` are the hours it keeps to itself and the exceptions carved out of them, `--on-paused` says whether work already running is stopped or left to finish, `--track BRANCH` follows a branch rather than releases and restarts itself when nothing is running, and `--persist` installs it to start at logon instead of serving now |
