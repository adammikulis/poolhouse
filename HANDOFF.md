# Handoff

## Faster testing and landing, in order of use
1. **Share the `team` fixture's setup, not the node.** A bare `workspace_node` costs about 0.35 s to start and 0.1 s to stop (about 4.6 CPU minutes over 690 tests); the rest of a node test's setup is `team`: registering members, enrolling the person key, and `board create` / `join-board` as subprocesses (0.6 s per test in `test_board_messages`, 1.6 s in `test_workspace_files`, where sharing the person key helps most). A module-scoped node is not safe as it stands: one shared board is not isolated because claims, announcements, digests and rooms are board-wide. A node that makes a fresh board for each test also meets the 32 boards one process tree may make (`MOST_BOARDS_PER_LINEAGE`): a board whose session ended is removed only once it has been quiet for `board_grace_s` (an hour), so a module-scoped node needs `board_grace_s` set to 0 in its `write-limits.json` or a board name per module.
2. **`tests/test_gates_incremental.py` (about 316 s and 109 s on one worker)** runs eight incremental runs, each followed by a whole-repo full run. No run could be proved redundant: the cold pyright run fills the cache the last incremental run depends on, and the real-tree test covers roots the copy lacks. Leave it unless a checker is shown to repeat another's work.
3. **About 5 s of a scoped run sits outside pytest:** three small files take 24.3 s inside pytest (fixed 3.6 s) and 29.6 s on the wall clock. Time the runner's start (`scripts/test` before the `+ python -m pytest` line) and its end (reuse record, evidence file, junit read) and fix what is above 2 s. The 20 s in that run is one test, `test_budgets.py::test_metric_is_within_its_budget[pyright-errors]`, which is real work.
4. **Re-record `tests/ci-durations.json` from a complete CI run** (`scripts/ci_shards.py record --junit`): it comes from local history that counts child CPU, so shard 4 is overloaded and some files are 3 to 10 times off. This only matters for the nightly and pull-request runs.
Not worth doing: cutting parametrized cases (under 3 percent of the time), deleting tests (the cost sits in about 150 heavy tests, not in the count), and the landing path (a push waits for nothing).

## Node limits, what is left
- **Log rotation is built on `feat/log-rotation` and waits for a non-author's attack pass (`docs/notes/2026-10-19-log-rotation.md`, section 5), then for `Node.pool` (a base binds no pool until heads sign one).** What it leaves: the idem key of a row that moved to the archive is gone (a request retried after a segment start writes again); a restated note has a new id, so a reply or a supersede that names the old id points into the archive; messages, audit, landing, lease and identity rows leave the view at the base; a copy behind a base whose archive is gone moves past the missing rows only when the device that wrote the log sends the base, so a device that cannot reach it waits; `Node.log_rotate_percent` is on for every node and the test kit sets it to 0 (a Rust test that fills a log to its bound must do the same); the archive of a copy is read whole for each batch it serves.
- **A board with entries, or one another device synced, is never removed.** `Node::reap_idle_boards` removes only a board that holds nothing but the starts and ends of its sessions and that no other device ever synced; a board with a message, a note or any other entry, and a board another device holds a copy of, stay for ever, and count toward `MOST_BOARDS_PER_LINEAGE` of the tree that made them. `Node::open` still hosts every directory under `boards/`. Needs lazy hosting (a board is opened when a session registers or a peer syncs it) and a way for a pool's devices to agree that a board with entries is finished.
- **The local socket has no connection cap.** `server.rs` starts one thread per connection; a cap needs a choice between refusing with a sentence (the refusal frame can be lost to a reset when the client's request is still unread) and not accepting until a place is free (the client waits, with no sentence).
- **The author share does not reach a foreign log.** A copy of another device's log is held to the rows and bytes a device keeps in all (`Bounds::admit_copy`), but the rows of one author in it are not counted: they come signed and are taken whole.
# Release cut
- **Two audiences, one build:** a person on the desktop or phone app taps and reads plain sentences and never meets a terminal, key or port; a developer using the library keeps their workflow with no new flag, prompt or wait, and gets the same protection. A release item that adds a visible step for either is redesigned first.
- **Existing harnesses are the way in:** Claude Code, Codex and other coding agents work through hooks, settings and the library with no change to how they are launched or used; the release is checked by driving one of them through a pool journey, not by tests alone.
- **Blocks a release:** the release signing key (owner terminal); `scripts/github-protection-apply` (owner terminal); a pool founded, joined and approved with no phone (a trusted computer's key signs the charter; a phone is an optional extra); the access-widening residue below; the isolated launcher's slices L1 to L5 (`docs/design-isolated-launcher.md`: egress proxy, sandbox, and the rest of the path a hostile model's agent runs through). The Box slices (B2, B4, B5, B6) are not part of 0.3.
- **Access widening, what is left:** every command an agent types meets a guard, and a program an agent writes and runs does not, because the guards read names. Such a program can read the lead's token file and the person record's key and write `authority.json`, and a process under a pseudo-terminal it owns, with the agent markers removed, can answer the typed yes of `person.typed`. The cures are the agent sandbox (`docs/agent-sandbox.md`; the owner runs its acceptance steps) and, for the authority registry and the person-only commands, a prompt the node draws with the registry held by the node (the presence step in `app/poolhouse-node/src/presence/` reaching past the first key and phone; it needs a design and a non-author attack pass first). The Monitor and tool-guard wiring was tested with the real hooks and was not driven in a Claude Code session of its own.
- **A refused or shut-down pool is deleted after 3 days** (owner, 2026-10-13), kept until then so a person can change their mind; the node does the delete, and a person can restore it inside the window. A pool shut down for compromise is frozen, sealed read-only with its keys and grants revoked, never restorable, and a person founds a new one; the 3 days delete only its live state and secrets, and the sealed record stays until a person deletes it (owner, 2026-10-13). Not built.
- **Not in the first release:** the Box enforcer, decoys, two-box layering and lab mode (no code or design document for them is in the repository); the default stays the Poolhouse proxy and kernel sandbox.
- **The scripts that check a push start Python with the pushing environment's `PYTHONPATH`:** `scripts/hooks/pre-push` starts `pushed` and `person-consume` as `"$python" script` with no `-I`, so a `sitecustomize.py` or a `shlex.py` that the environment puts first runs before the check and can end it with status 0. A person edits `pre-push` (a guard file) to start both with `"$python" -I`.

- **Known limits of slice 1, from the attack-first review (2026-10-11), each in `docs/node.md` "Who governs a pool":**
  - The rate of a delegate (3 an hour, 10 a day) and of an open pool's member (5 an hour) is counted by the order each device first saw the admits, so two devices holding the same acts can disagree about which of four admits in an hour stand; a compromised delegate can choose the order it delivers them in. A pool-wide count needs the admits to carry a signed counter, which is not built.
  - Removing a device removes everything it admitted as a delegate or an open pool's member, transitively; an admin admits those devices again. `ended` delegates keep theirs.
  - The rule that a delegate's key lives in a keystore is enforced by the delegate's own node (`Node::key_binding`); a copy of a state directory with the file key, or any process holding it, signs a delegate admit once an admin names that device. `how` in an admit (`found`, `tap`, `join-code`, `open`...) is whatever its signer wrote.
  - A `veto` by the key a removal names pauses the admin-set acts for seven days, and a stolen admin key can veto each new removal of itself; the recovery path that ends it is slice 3.
  - The join code's three tries can be burned by any TLS client that does not know the code; `on_segment` counts loopback (and, on Windows, any RFC 1918 address), so an open pool admits local processes by design.
